# Обязательные RLS-проверки до запуска с настоящими пользователями

Схема находится в `supabase/migrations/20261028_120000_direct_messages.sql`.

После подключения **dev** проекта создать как минимум 3 подтверждённых тестовых аккаунта A, B, C через Supabase Auth и выполнить следующие проверки в среде с их реальными JWT (не через service role, которая обходит RLS):

1. Гость (`anon`) не читает `profiles`, `chats`, `chat_members`, `messages` и не вызывает `start_direct_chat`.
2. A и B сохраняют свои профили; A не может менять профиль B. Идентичные `username` отвергаются уникальным ограничением.
3. A запускает чат с B, повторный запуск B→A возвращает тот же `chat_id`. Запуск A→A отвергается.
4. C **не может** прочитать чат A/B, строки `chat_members` или сообщения чата A/B.
5. C **не может** отправить сообщение в чат A/B; A и B могут. A не может подставить `sender_id` пользователя B.
6. C не может напрямую создавать `chats` и `chat_members`; A не может удалить чужое сообщение.
7. Подписка Postgres Changes отдаёт INSERT сообщения только A и B; C не получает содержимого.
8. В Safari и Android Chrome после подтверждения email проверить регистрацию, сохранение профиля, выход/вход, сообщение A→B и B→A, повторное открытие и сохранённую историю.

**Эти проверки пока не проведены.** Зелёный CI GitHub проверяет код и статические файлы, не доступ к живой базе и не фактическую безопасность RLS.

Для эксплуатации в РФ отдельно определить законную схему первичного сбора/хранения персональных данных граждан РФ. Не приглашать реальных граждан РФ в иностранный облачный экземпляр только ради тестирования.
