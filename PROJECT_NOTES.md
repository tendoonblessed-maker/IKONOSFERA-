## Функциональная карта исходного кода

- **Личные чаты:** сообщения, ответы/цитаты, реакции, редактирование и удаление, отметки прочтения, поиск, история с пагинацией, черновики, вложения и голосовые сообщения.

- **Профили и социальные функции:** username, фотографии, истории, контакты, блокировка и эмодзи-статусы.
- **PWA и мобильный интерфейс:** manifest, Service Worker, адаптивная навигация, safe areas и обработка мобильной клавиатуры.

Наличие функции в исходном коде не означает, что её поведение прошло ручную проверку на всех браузерах или устройствах.

## Архитектура и серверные границы

- Клиент использует Supabase Auth, PostgREST и Storage по HTTPS; доступ к приватным строкам/объектам должен оставаться под серверными RLS/Storage policies.
- Миграции и политики в Git находятся в `supabase/migrations/`. **Файлы миграций не доказывают состояние подключённой live-базы.** Перед любыми работами с БД требуется отдельная проверка целевого проекта и окружения.
- Не помещать service-role ключи и секреты в `NEXT_PUBLIC_*`, клиентский код, логи или тестовые фикстуры.
- Не заявлять о сквозном шифровании (E2EE): оно не реализовано и не подтверждено аудитом.
- Не считать клиентские проверки заменой RLS. Не расширять доступ к таблицам или Storage ради исправления UI.
- Не выполнять SQL, миграции, изменения схемы/RLS/Storage или действия с production в рамках обычного UI/качества PR.

## CI и локальные проверки

Актуальные команды из `package.json`:

```bash
npm install --no-audit --no-fund
npm run typecheck
npm run lint
npm test
npm run build
```

- `npm run lint` запускает `scripts/lint.mjs` — проектный policy-lint; это не ESLint.
- `npm test` запускает Node test runner по `tests/*.test.mjs`.
- GitHub Actions workflow: [Checks](.github/workflows/check.yml). Успешная сборка Preview сама по себе не подтверждает тесты/typecheck; для каждого PR сверять workflow с финальным HEAD.
- На дату этой проверки combined status `main` показывал Vercel SUCCESS; GitHub Actions workflow-run endpoint не вернул run для SHA `5f8f07f`. Поэтому не записывать полный CI `main` как PASS без отдельного подтверждения.
- Для PR проверять именно финальный HEAD, а не результаты предыдущего коммита. При изменении HEAD старые CI-результаты не переносить.

## Ручная проверка, которую CI не заменяет

Перед релизным объединением проверять на реальных устройствах/браузерах, где это применимо:

- iOS Safari и установленная PWA: фон/возврат, сеть, клавиатура, микрофон, медиа и safe areas.
- Android Chrome/WebView/PWA: те же сценарии, особенно permissions, media lifecycle и viewport.
- VoiceOver/TalkBack и клавиатурную навигацию для диалогов, поиска, вложений и live regions.
- Два отдельных тестовых аккаунта в изолированном staging: приватность, RLS, переключение аккаунтов, доставка и повторы сообщений.

Если staging или устройство недоступны, фиксировать это как ограничение, а не объявлять сценарий проверенным.

## Безопасные инженерные правила

- Работать в отдельной ветке; PR направлять в `main`, если нет явно указанной stacked-зависимости.
- Не менять production и не использовать реальные пользовательские данные.
- Не выполнять опасные/неподтверждённые миграции.
- Не использовать production как тестовую среду.
- Сохранять пользовательские сообщения и вложения при неопределённом результате сетевой операции; лучше явно показать неопределённый статус, чем удалять уже привязанный объект или автоматически дублировать отправку.
- После каждого принятого инженерного изменения обновлять эти заметки и оставлять точные ссылки на коммиты/PR/CI.
