# IKONOSFERA — мессенджер

> **Актуально для `main` на 29.10.2026.** Это действующий код веб-мессенджера, а не прототип «этап 0». Описания начальной PWA-заготовки перенесены в [архив](docs/archive/README_STAGE0_2026-10-28.md). Прежде чем делать выводы о функциях, смотрите актуальный код, миграции и результаты CI.

IKONOSFERA — адаптивный веб-мессенджер/PWA на **Next.js 16 (App Router), React 19, TypeScript, Tailwind и Supabase**. Интерфейс рассчитан на браузер iPhone, Android и компьютер; это **не** отдельные нативные приложения для App Store и Google Play.

- Production URL: **https://ikonosfera.vercel.app** (опубликованный коммит может отличаться от самого свежего `main` — проверяйте Vercel Deployments).
- GitHub: [tendoonblessed-maker/IKONOSFERA-](https://github.com/tendoonblessed-maker/IKONOSFERA-).
- История развития: [коммиты](https://github.com/tendoonblessed-maker/IKONOSFERA-/commits/main), [Pull Requests](https://github.com/tendoonblessed-maker/IKONOSFERA-/pulls), [GitHub Actions](https://github.com/tendoonblessed-maker/IKONOSFERA-/actions).

## Как устроена связь с сервером

Клиентский код работает с Supabase Auth, PostgREST и Storage по HTTPS. Сообщения и списки обновляются запросами/периодической синхронизацией; **не следует утверждать, что все сообщения работают через WebSocket/Realtime**, пока конкретный механизм не проверен. Серверный доступ контролируют права пользователя и RLS, а не одна только проверка интерфейса.

Личные сообщения поддерживают **серверные ответы** через `reply_to_message_id`, с проверкой принадлежности одному чату и защитой доступа через RLS. Это требует миграции `20261029_073000_direct_message_replies.sql` **до** публикации фронтенда с новым полем. На уже опубликованном сайте может оставаться более старая версия с ответами-цитатами в тексте. И не следует заявлять о сквозном шифровании (E2EE) или готовности к неограниченным нагрузкам без отдельной реализации и аудита.



Поиск внутри личной переписки теперь использует отдельную серверную функцию `search_direct_messages` из миграции `20261029_080000_direct_message_full_history_search.sql`. Она ищет **буквальный текст** (без интерпретации % и _ как масок), проверяет членство в чате, применяет RLS, исключает удалённые сообщения и возвращает ограниченные страницы результатов. Примените миграцию **перед** публикацией клиентской функции. Поиск не распространяется автоматически на все чаты, каналы или групповые переписки.

## Доставка обновлений в личных чатах

Для **открытого личного диалога** подключается один авторизованный канал Supabase Realtime (Postgres Changes) с фильтром по `chat_id`. В базе применена миграция `20261029065959_enable_direct_message_realtime`, включающая в публикацию `supabase_realtime` только таблицу `public.messages`.

События `INSERT` и `UPDATE` лишь запускают повторный запрос сообщений: серверные правила RLS по-прежнему решают, кому можно читать переписку. Данные события не используются напрямую для формирования сообщений на экране. При переподключении переписка синхронизируется заново. Если WebSocket недоступен, **обычный HTTP-опрос каждые 6 секунд остаётся рабочим**; после переключения диалога или аккаунта предыдущая подписка закрывается.

Это **не** сквозное шифрование. Уведомления списка чатов и групп уже обновляются через Realtime, но каналы, закрытое приложение и push-уведомления пока работают отдельно. Общий список личных диалогов по-прежнему синхронизируется отдельно. На масштабном производстве стоит рассмотреть Supabase Broadcast с приватными темами вместо Postgres Changes для меньшей нагрузки.

## Живой список переписок и непрочитанных сообщений

Общий список личных диалогов и групп теперь слушает авторизованные события Supabase Realtime для `public.messages` (`INSERT` и `UPDATE`) и `public.group_messages` (`INSERT`). События **не содержат отображаемых клиентом сообщений**: это только сигнал для стандартных запросов `list_chat_previews`, `list_active_chats` и `list_group_overviews`, которые соблюдают действующие RLS-политики.

Обновления объединяются с небольшой задержкой, чтобы десятки событий не порождали десятки запросов. Ответы старых запросов игнорируются, если новый запрос уже стартовал или аккаунт сменился. При отсутствии WebSocket продолжает работать регулярный опрос (общий список — раз в 12 секунд, группы и прочие данные — реже). Подписка существует только в открытом приложении, не заменяет push-уведомления и не обеспечивает сквозного шифрования.

В работающем Supabase уже опубликованы обе необходимые таблицы после миграций `20261029065959_enable_direct_message_realtime` и `20261029071053_enable_group_message_realtime`; для списка дополнительных SQL-прав не требуется. Для большого количества пользователей рекомендуется рассмотреть приватные Broadcast-темы вместо подписок Postgres Changes на все доступные сообщения.

## Черновики групп и адаптивный редактор

Как и личные переписки, групповые чаты сохраняют набранный текст только в **sessionStorage текущей вкладки**. Черновики отделены по `userId` и `groupId`, не отправляются на сервер и очищаются при выходе из аккаунта. На главном экране строка группы отображает метку «Черновик», когда есть неотправленный текст.

Редактор группы теперь поддерживает несколько строк: **Enter** отправляет на компьютере, **Shift+Enter** добавляет перенос строки, **Ctrl/Cmd+Enter** отправляет и на других устройствах. Мобильная клавиатура не должна увеличивать масштаб страницы из-за маленького шрифта. Если соединение пропало, отправка блокируется, но текст сохраняется. При редактировании черновика во время предыдущей отправки новый текст не очищается.

Исследованные репозитории Telegram, Swiftgram, Nicegram и неофициальные библиотеки WhatsApp, совместимость лицензий и план безопасного переноса подходов документированы в [матрице открытой инфраструктуры](docs/OPEN_SOURCE_INFRASTRUCTURE.md). Исходники чужих GPL-клиентов не скопированы.

## Защита групповых сообщений от дублей при повторной отправке

Теперь у каждой конкретной **попытки отправить групповой текст** есть клиентский UUID, сохраняемый во временном `sessionStorage` вкладки. При потере ответа сервера и ручном повторном нажатии с неизменным текстом используется **тот же UUID**, а PostgREST `on_conflict=id` и `Prefer: resolution=ignore-duplicates` позволяют вставить сообщение не более одного раза для этого ID. Изменённый текст получает новый UUID; после подтверждённой успешной отправки запись попытки очищается.

Если сервер не вернул подтверждение из-за обрыва сети, клиент делает авторизованный GET по ID и проверяет точное совпадение автора, группы и содержимого. Когда результат не удалось проверить, сообщение **не отправляется автоматически**: исходный черновик остаётся на экране с кнопкой «Повторить отправку». После перехода в другую группу или нажатия «Выйти» попытки ограничены соответственно текущим контекстом/аккаунтом. На стороне базы используется существующий первичный ключ `group_messages(id)` и правила RLS по `is_group_member(group_id)` — новая миграция и расширенные права не нужны.

Ограничения: такой UUID защищает от дублей именно при повторении **одной сохранённой попытки в той же вкладке**. После удаления данных вкладки, истечения 48 часов или существенного редактирования черновика создаётся новая попытка. Результат отправки при невозможности связаться с сервером может остаться неизвестным до следующей проверки.

## Корректное прочтение групповых сообщений и возврат к новым

Когда человек прокрутил групповой чат к старым сообщениям, **новые входящие больше не отмечаются прочитанными только потому, что пришли по Realtime/HTTPS**. `mark_group_read` вызывается лишь тогда, когда история видна и пользователь находится у последних сообщений. При возвращении вниз непрочитанное подтверждается стандартным серверным RPC (участие в группе проверяет прежняя RLS/схема). Существующая модель `group_members.last_read_at` не менялась.

Для групп добавлена плавающая кнопка **«К последним сообщениям»** и счётчик новых сообщений, поступивших во время просмотра старой истории. Счётчик учитывает новые сообщения других участников и не считает исходные сообщения первой загрузки. Кнопка прокручивает **только контейнер истории**, не всю страницу Safari, и возвращает привычный автоматический скролл. При переключении группы или аккаунта индикатор сбрасывается. Запросов к серверу сверх существующих не добавлено.

## Быстрые обновления групп

После миграции `20261029071053_enable_group_message_realtime` активная группа получает подписку на `group_messages` с фильтром по `group_id`. Подписка использует существующий токен пользователя; серверная RLS-политика `is_group_member(group_id)` определяет доступ. **Тело сообщения не берётся из WebSocket-события**, а загружается через стандартный HTTPS API. Это защищает от неавторизованного отображения чужих сообщений и автоматически учитывает изменения прав участника.

Сообщение, подтверждённое сервером при отправке, сразу видно в группе — дополнительный GET больше не требуется. Защита от запоздавших ответов устраняет краткое исчезновение новых сообщений. Если Realtime не подключается, остаётся синхронизация раз в 6 секунд. При смене группы/аккаунта подписка удаляется. Это изменение пока не добавляет сквозное шифрование или уведомления в фоне, когда приложение закрыто.

## Голосовые сообщения в личных чатах

В открытом личном диалоге кнопка микрофона запускает запись браузерным `MediaRecorder` **только после разрешения пользователя**. Доступны таймер, отмена и завершение. Максимальная длительность — **2 минуты**, размер файла — **до 25 МБ**. После записи файл попадает в существующее окно предпросмотра: запись можно **прослушать или удалить до отправки**. Без подтверждения пользователя ничего не загружается в интернет.

В Chrome/Firefox используется Opus в WebM (или поддерживаемый Ogg); в Safari — аудио MP4/AAC. Формат определяется через `MediaRecorder.isTypeSupported`. При отсутствии поддержки, HTTPS или разрешения микрофона выводится сообщение об ошибке, переписка продолжает работать. При смене аккаунта/чата, блокировке или отмене все дорожки микрофона останавливаются; запись не сохраняется в `localStorage` и не загружается в фоновом режиме. Во время остановки ожидаем финальные фрагменты данных `MediaRecorder`, после чего открываем предпросмотр.

В действующем Supabase применена миграция `20261029081406_allow_private_voice_audio_webm`: к разрешённым форматам существующего **приватного** бакета `ikonosfera-direct-media` добавлен только `audio/webm`. Доступ к файлам по-прежнему ограничен RLS, временными ссылками и прежним лимитом. Голосовые сообщения пока реализованы **только для личных чатов** (в группах их нет). Для проверки на конкретных мобильных устройствах требуется ручное тестирование микрофона и воспроизведения.

## Ссылки внутри сообщений

В личных чатах и группах адреса `https://`, `http://` и `www.` стали **кликабельными**. Ссылки открываются в новой вкладке с `rel="noopener noreferrer nofollow ugc"`, сокращение `www.` открывается по HTTPS. Некорректные адреса, ссылки с логином и паролем, а также `javascript:`, `data:`, `file:` и другие схемы не становятся активными ссылками.

Реализация **не вырезает HTML из текста пользователя** и не выполняет HTML-парсинг: React выводит исходный текст с экранированием, поэтому записи вроде `a < b`, код и переносы строк остаются видимыми. Длинные адреса переносятся внутри пузыря сообщения; завершающая пунктуация не попадает в ссылку. **Сайт по ссылке не запрашивается сервером и не загружается для предпросмотра** — переход происходит только при явном нажатии. Никаких новых ключей, таблиц или разрешений Supabase не требуется.

## Вложения в личных чатах

Файлы теперь **сначала открываются в окне предпросмотра**: можно проверить фото, видео или аудио, добавить подпись и только затем подтвердить отправку. На компьютере поддерживаются перенос файла в открытую личную переписку и вставка изображения из буфера обмена (Ctrl+V). Предусмотрены отмена и повтор отправки при ошибке; уже набранный текст основного поля не подменяется подписью. Форматы и лимит **25 МБ** проверяются и при выборе, и непосредственно перед загрузкой. В групповом чате и каналах эти способы прикрепления пока не включены.

## Локальный запуск

Нужны Node.js (версию уточняйте по `package.json`) и npm. Создайте `.env.local` самостоятельно:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
```

**Никогда** не записывайте Supabase service-role key, пароль БД, refresh token или другие секреты в `NEXT_PUBLIC_*` или GitHub.

```bash
npm install --no-audit --no-fund
npm run dev
```

Откройте http://localhost:3000. Если переменные окружения отсутствуют или backend недоступен, функции переписки не будут работать корректно.

## Развёртывание и работа с данными

- Production подключён к Vercel, но **`main` и реально опубликованная версия могут различаться**, например из-за ограничения числа развёртываний. Перед заявлением «обновление на сайте» проверяйте `READY`, SHA коммита и алиас `ikonosfera.vercel.app`.
- Любые изменения таблиц выполняйте отдельными миграциями с учётом существующих RLS-политик, зависимостей и данных. Никогда не запускайте разрушительные миграции в production без проверки.
- Для обновлений создавайте отдельную ветку, открывайте PR и дожидайтесь CI. Не сбрасывайте историю и не публикуйте непроверенный код.
- Не считайте старые незакрытые PR источником текущей функциональности: некоторые уже реализованные изменения могут присутствовать в `main` независимо от состояния тех PR.
