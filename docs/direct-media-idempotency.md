# Личные вложения: безопасный повтор после потери ответа

## Поведение

Для одной отправки клиент вычисляет SHA-256 файла и метаданных (MIME, размер,
имя, \`lastModified\` и точная подпись). По этому отпечатку создаётся
стабильный \`client_message_id\`, изолированный по аккаунту и чату.
В \`sessionStorage\` хранится только отпечаток, UUID и время попытки —
не файл, подпись или токен. Срок хранения — 48 часов, максимум 8 попыток
на чат. Незавершённые отпечатки остаются привязаны к UUID аккаунта до подтверждения или истечения TTL, в том числе после выхода; другой аккаунт их не читает. Если хранилище недоступно, действует резервная память вкладки.

Объект Storage получает детерминированный приватный путь:

\`\`\`text
<chat UUID>/<sender UUID>/<client_message_id>.<extension>
\`\`\`

Если ответ Storage потерян, клиент проверяет этот точный путь короткой
подписанной ссылкой. Если объект существует, повторная загрузка не нужна.
Если не существует, пользователь может вручную повторить отправку.

Строка \`messages\` вставляется с тем же \`client_message_id\`. При
неопределённом ответе выполняется только читающий RLS-scoped SELECT по
\`chat_id + sender_id + client_message_id\`. Принимается ровно одна
строка, полностью совпадающая по автору, чату, ID попытки, подписи, пути
объекта и типу. Повторного автоматического INSERT нет; ручной повтор
использует тот же UUID и существующий уникальный индекс \`(sender_id,
client_message_id)\` не позволяет создать вторую строку.

Удаление объекта допускается только после определённого 4xx-отказа INSERT
и успешного read-back, вернувшего пустой результат. При сетевой ошибке,
5xx, тайм-ауте, конфликте или неудачном read-back объект сохраняется:
удалять его, пока неизвестно, записано ли сообщение, небезопасно.

## Ограничения

- После перезагрузки вкладки пользователь должен заново выбрать тот же файл
  и ввести ту же подпись; браузер не позволяет восстановить объект \`File\`.
- При заблокированном \`sessionStorage\` восстановление действует только
  до закрытия/перезагрузки вкладки.
- Изменение файла или подписи создаёт новую отправку. Старую попытку нельзя
  считать отменённой, если её ответ был потерян.
- Нужен Web Crypto (\`crypto.subtle\`) и HTTPS. Автоматическая отправка
  после восстановления сети не выполняется.
- Проверки используют текущую RLS. Перед выпуском требуется staging-smoke
  test с двумя тестовыми аккаунтами и реальными тестовыми файлами.

Изменения ограничены клиентским кодом и регрессионными тестами. Выход не стирает только digest/UUID незавершённых медиа-попыток: это необходимо, чтобы поздний commit старого запроса не превратился в дубликат после повторного входа того же аккаунта. Схема БД,
RLS, Storage policies, production и пользовательские данные не меняются.
