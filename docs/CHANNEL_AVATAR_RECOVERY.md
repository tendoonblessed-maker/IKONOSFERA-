# Аватарка канала: защита от потери подтверждения

## Что было не так

При смене аватарки канал сначала сохраняет новый файл в Supabase Storage,
затем меняет `channels.avatar_path`. Старый UI в `ChannelsPanel` в блоке
`catch` безусловно удалял загруженное фото. Если PATCH **успел сохраниться**
в PostgreSQL, но HTTP-ответ потерялся, это удаляло уже используемое фото:
в канале или списке отображался значок-заглушка.

Дополнительно подробная страница проверяла только `avatar_path` на
непустую строку, а не валидность `imageUrl(path)`, и использовала старое
`channel.description` вместо обновлённого `currentChannel.description`.

## Исправление

- После PATCH `updateChannelAvatar` проверяет возвращённую запись по
  `id`, `owner_id`, точному `avatar_path`.
- Если HTTP-ответ потерян, PATCH вернул пустую/несовпадающую запись или
  произошёл тайм-аут, клиент делает **одну читающую** проверку
  `getChannelById` под обычным пользовательским JWT и RLS.
- Серверный результат подтверждает операцию, только если канал, владелец
  и адрес изображения совпадают с запрошенными.
- Ни при каком неоднозначном результате новый файл **не удаляется**:
  отправленный PATCH уже мог быть принят. Ошибка остаётся видимой, а
  последующий вход в настройки показывает авторитетные данные с сервера.
- На странице канала и у постов некорректный адрес не превращается в
  `<img src={undefined}>`: вместо него показывается `#`.
- Ограниченный по времени запрос защищает UI от бесконечного ожидания.

## Известные ограничения

- После недоставленного ответа и неподтвердившегося PATCH в хранилище
  может остаться неиспользуемое изображение. Без безопасной серверной
  проверки ссылок удалять такие объекты нельзя.
- Два одновременных изменения одним каналом на разных устройствах не
  координируются; более поздний подтверждённый PATCH может изменить путь.
- Пока нет сквозного ручного теста на iOS Safari, Windows и staging Supabase.
- Не меняет RLS, схему БД, конфигурацию Storage и production.
