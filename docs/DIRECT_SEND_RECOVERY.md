# Личные сообщения: безопасный повтор после потери ответа — 29.10.2026

## Проблема
Клиент уже передавал `p_client_message_id` в `send_direct_message`/
`send_direct_reply`, а Postgres обеспечивал уникальность пары
`(sender_id,client_message_id)`. Однако интерфейс генерировал новый UUID
при каждом нажатии «Отправить». При потере ответа после успешной записи
повторная попытка могла создать дубль.

## Решение без изменения БД
- `lib/direct-send-attempts.ts` хранит ID, тело, reply target и дату попытки
  в `sessionStorage` текущей вкладки отдельно для каждой пары аккаунт/чат,
  с памятью на случай блокировки storage. Срок жизни — 48 часов.
- Та же комбинация текста и reply target повторно использует **тот же UUID**.
  Изменённый текст или другая цитата получает новый UUID; закрытый ответ на
  цитату не превращается без предупреждения в обычное сообщение после reload.
- `postMessage` строго проверяет возвращённую запись: chat, sender, body,
  client ID и quoted message ID. При неоднозначном network/5xx/408/429
  исходе **не** делает второй POST автоматически: один ограниченный
  `SELECT` по chat+sender+client ID под прежней RLS может подтвердить уже
  сохранённую запись. При отсутствии подтверждения остаётся ручной повтор.
- После успешного ответа ID стирается только при точном совпадении.
  Позднее подтверждение не может стереть новую попытку. Черновик нового
  сообщения или другого пользователя не изменяется.
- В окне переписки появляется маленькая кнопка «Повторить отправку».
  Интернет восстановился — автоматической рассылки не происходит.
- При выходе удаляются попытки только текущего пользователя.

## Ограничения
- Это решение охватывает **текстовые личные сообщения и текстовые ответы**.
  Файлы, голосовые сообщения и медиа — отдельный поток; не обещаем для них
  exactly-once.
- Повтор после изменения текста означает **новое сообщение**. Старый POST
  мог успеть сохраниться. Редактируйте при необходимости уже отправленную
  запись, а не считайте отменённым неоднозначный запрос.
- Состояние на одной вкладке не координирует отправки с другого устройства.
- GET-проверка использует текущие RLS и ограничения видимости; она не
  читает чужую историю. Ключ сервисной роли не нужен.
- Полная end-to-end проверка на двух JWT, iOS Safari и Windows Chrome
  перед публикацией обязательна.


пользователя/чата; Safari без sessionStorage; отмена и редактирование цитаты;
сеть пропала/вернулась без автоотправки.
